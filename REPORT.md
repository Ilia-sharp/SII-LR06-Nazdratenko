# Отчёт по лабораторной работе «Рекомендательные ИИ-системы»

**Вариант 16.** Условие: `visitorid % 30 = 15`.
Сценарий: «Один источник истории». Индивидуальное условие: использовать
только последние события пользователя. Выдача: Top-10.
Автор: Nazdratenko. Репозиторий:
<https://github.com/Ilia-sharp/SII-LR06-Nazdratenko>.

## 1. Цель и индивидуальный вариант

Цель — освоить базовый цикл разработки рекомендательного сервиса на
событийных данных: загрузка и анализ событий, популярностная и
item-item/co-visitation модели, временная оценка Top-N и выдача результата
через CLI/HTTP API.

Индивидуальное условие варианта 16 ограничивает источник истории: контекст
строится только по последним событиям самого `visitorid`, без смешивания с
сессиями других пользователей. Из выдачи исключаются товары, уже
встречавшиеся в истории пользователя.

## 3. Очистка, временное разделение и сессии

**Очистка.** Проверены обязательные колонки, приведены типы (`visitorid`,
`itemid` — int64; `timestamp` — datetime UTC), удалены полные дубликаты,
отброшены строки с неизвестными типами событий (в данном файле их нет),
данные отсортированы по времени. `transactionid` не используется как признак.

**Временное разделение.** Последние 20% временного диапазона — test,
остальное — train:

```
cutoff = max(ts) − 0.2 × (max(ts) − min(ts))
```

Перемешивания нет. Train: 2 266 031 строк (82.23%), test: 489 610 строк
(17.77%), граница — 2015-08-21 12:35:51 UTC. Доля строк в test меньше 20%
из-за роста трафика, но все test-события строго позже train.

**Сессии.** Сессия — события одного пользователя с разрывом не более
**30 минут**; новый посетитель начинает новую сессию. На train —
1 436 517 сессий, в среднем 1.577 события, максимум 417.

## 4. Алгоритмы и параметры

### 4.1. Популярностный baseline

На train суммируются веса событий по каждому `itemid`:

```
score(item) = 1·view + 3·addtocart + 5·transaction
```

Сортировка по убыванию score, при равенстве — по возрастанию `itemid`.
Из Top-10 удаляются товары из истории пользователя.

### 4.2. Item-item / co-visitation

В каждой train-сессии берутся уникальные товары в хронологическом порядке;
каждая пара увеличивает совместную частоту на 1. Матрица симметричная.
В очень длинных сессиях учитываются последние 50 уникальных товаров —
инженерное ограничение против квадратичного роста (затрагивает доли
процента сессий).

Получено: словарь 215 683 товара, 2 004 561 вхождение пар, 1 724 569
уникальных пар, в среднем 15.99 соседа на товар.

Скор кандидата:

```
score(c) = Σ weight(context_item) · co_visit(context_item, c)
```

где `weight` — вес события контекста (1/3/5). Кандидаты из истории
исключаются, остаются Top-10.

### 4.3. Контекст варианта 16

Берутся **последние 5 событий пользователя**, дубликаты товаров
схлопываются с сохранением самого свежего события. Используется только
история этого `visitorid` — один источник истории. Сессии других
пользователей применяются только для обучения co-visitation.

### 4.4. Оценка

Целевая группа — `visitorid % 30 = 15`. Цели — уникальные товары из
`addtocart` и `transaction` в test; `view` — только контекст.
Для каждого пользователя контекст и история берутся строго **до первого
целевого события test**. Модель обучена только на train; более ранние
события test допустимы как контекст, потому что они уже произошли к моменту
выдачи. Целевые события в контекст не попадают.

Формулы:

```
Precision@10 = |Top-10 ∩ Target| / 10
Recall@10    = |Top-10 ∩ Target| / |Target|
NDCG@10      = DCG@10 / IDCG@10,  rel ∈ {0, 1}
DCG@10       = Σ rel_i / log2(i + 1)
```

Обе модели оцениваются на одних и тех же пользователях: 226 целевых
посетителей, 48 cold start, 178 в оценке. Средняя длина контекста — 1.79.

## 5. Результаты

| Модель | Precision@10 | Recall@10 | NDCG@10 | HitRate@10 |
|---|---:|---:|---:|---:|
| Popularity baseline | 0.000562 | 0.000268 | 0.001236 | 0.005618 |
| **Item-item / co-visitation** | **0.006180** | **0.021191** | **0.015219** | **0.056180** |

Co-visitation превосходит baseline примерно в 11 раз по Precision@10,
в 12 раз по NDCG@10 и в 10 раз по HitRate@10.

### Вспомогательный срез без уже виденных товаров

46.8% пар «пользователь–цель» уже присутствовали в истории до выдачи
(типичный сценарий: просмотр, затем покупка того же товара). По требованию
лабораторной такие товары нельзя рекомендовать, поэтому они заведомо
являются промахами. На 209 «новых» целях (43 пользователя):

| Модель | Precision@10 | Recall@10 | NDCG@10 | HitRate@10 |
|---|---:|---:|---:|---:|
| Popularity baseline | 0.002326 | 0.001163 | 0.005118 | 0.023256 |
| **Item-item / co-visitation** | **0.025581** | **0.124636** | **0.078371** | **0.232558** |

Здесь co-visitation уже в 11 раз лучше по Precision и в 10 раз по NDCG;
HitRate@10 — 23.3% против 2.3%.

## 7. Анализ ошибок и ограничений

* **Cold start.** У 48 из 226 целевых пользователей не было событий до
  первого целевого события. Они исключены из основной оценки; в API для них
  предусмотрен популярностный fallback.
* **История и повторные покупки.** Почти половина целей уже была в истории,
  а фильтрация истории обязательна. Это главная причина низкого Recall;
  вспомогательная таблица показывает качество на новых товарах.
* **Разреженность.** Средняя длина контекста 1.79 товара; большинство
  сессий — одно событие. Модель часто опирается на одну пару, поэтому score
  грубый и нестабильный.
* **Глобальная популярность.** Baseline не персонализирован; после
  фильтрации истории его топовые товары часто выбывают.
* **Ограничения.** Не используются `category_tree`/`item_properties` (не
  обязательны); длинные сессии обрезаются до 50 товаров; нет временного
  decay и онлайн-обновления; нет категорийных baseline.
* **Утечки.** Разделение только по времени; популярность и co-visitation
  строятся только на train; контекст оценки строго до целевого события;
  целевые события test не участвуют в обучении и контексте. `visitorid`
  анонимный: используется только остаток по модулю 30 для выбора группы,
  его величина не является признаком.

## 8. Запуск и воспроизводимость

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt

# events.csv положить в data/ (в репозиторий не коммитится)
python -m src.cli train --events data/events.csv --artifacts artifacts
python -m src.cli evaluate --artifacts artifacts
python -m src.cli recommend --artifacts artifacts --visitor-id 582525
python -m src.cli serve --artifacts artifacts --port 8000
```

Параметры: `test_fraction=0.20`, `session_gap_minutes=30`,
`context_size=5`, `top_n=10`, `max_session_items=50`, веса 1/3/5,
цель — `addtocart`+`transaction`. Полный прогон на 2.76 млн событий —
около 30 секунд на CPU. Все параметры и метрики сохраняются в
`artifacts/metadata.json`; датасет в репозиторий не входит, а готовые
артефакты модели закоммичены для демо на Render и пересобираются командой
`train`. Тесты: `pytest -q` (16 тестов).
